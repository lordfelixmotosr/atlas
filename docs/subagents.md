# Atlas helper teams

Helpers are available in ordinary mod workspace chats. Expand the Helpers row above the composer, or open Settings → Accounts & models → Helpers. Efficient mode and a maximum of four simultaneous helpers are the defaults. The limit applies across open chats; choose up to eight. Extra jobs queue fairly between chats. Sixty-four running/queued assignments are allowed at a time.

Ask the assistant for a feature normally, or explicitly ask it to delegate independent parts. For example: “Use helpers to inspect the C# behaviour and XML definitions, then implement and review this feature.” The lead can spawn research, implementation and review tasks, collect results, steer work and integrate patches. Simple changes need no helpers.

Efficient routes routine research to a known lighter model in the connected provider's available catalog. It never changes providers or signs into another account. If no suitable lighter model is listed, it keeps the main model and thinking setting. Implementation, review and complex research retain the main selection. Match main disables economical routing. Helper-specific effort never rewrites the main chat's requested thinking or global defaults. Each row shows its model, effort and routing reason. Catalog availability is not proof of subscription entitlement: a rejected request is reported without automatic model hopping. Atlas skips the observed unsupported GPT-5.4 mini ChatGPT route (not its separate API-key route), and explicit model-access failures in a chat's retained helper history exclude that model from later automatic selections. Retry reselects using that history, including after restarting Atlas. Queued helpers recheck their model when starting. Network, quota and ordinary tool failures do not exclude a model; a manually selected parent model is never replaced by this filter.

Helpers have separate, short conversations. They receive the assignment and project instructions, not the full parent chat transcript. The main assistant should give them requirements, relevant paths, shared identifiers and expected results. Their summaries return to the lead through helper tools. The UI also shows elapsed time, last activity, real status and token counts when supplied by the provider. Token counts are not a price or credit-balance estimate.

Research/review helpers have read and reference tools. Implementation helpers additionally receive write/edit/delete tools restricted to at most thirty assigned text files, including PowerShell, Python and shell-script source. Assignments are validated without creating staging or sending a model request; unsupported files return a specific path/type error to the lead for correction. Existing files must pass bounded UTF-8 and binary-content checks, and the same protections are checked again when work starts. Binary assets remain the lead's responsibility. Helpers cannot execute scripts, run shell commands, compile, launch a game, install, publish, or spawn another helper. The lead performs validation and game operations. Routine research has a 20-minute task budget; implementation, review and complex research have 30 minutes, starting when a slot becomes available. The running row shows time remaining and a manual Extend 15 min action, capped at two hours total. Extending time does not send another model request or change thinking. The provider watchdog is separate: ten minutes without any response data stops that request; response events reset its idle clock. A helper still has at most thirty model turns and no automatic retry after failure. Stop clears queued steering and cancels the whole chat team. Cancelling waits for child cleanup before reusing its slot or allowing account changes.

Edits are staged outside the mod under the portable profile's `pi-agent/helper-work` directory. Files are loaded on demand; Atlas does not duplicate an entire mod for each helper. Review opens a bounded patch preview with optional file paging. Integration checks the source files the worker read, the staged checksums and the reviewed patch fingerprint. Conflicts leave the project unchanged. Failed multi-file integration attempts restore previous files; failed rollback preserves recovery backups and reports the paths. Unapplied patches can be discarded from their Actions menu. If a stale or uncertain patch cannot safely be discarded, Atlas retires the assignment, retains its files and reports their location.

History is stored in `pi-agent/subagent-tasks.json`. A restart marks unfinished tasks interrupted. Explicit Retry creates a fresh task and checks file ownership again. Completed patches and checkpointed partial patches remain reviewable when their original file versions still match. In Helpers → Actions, Review saved work opens a bounded diff; Apply reviewed partial patch requires a separate click, and oversized diffs must be reviewed by the lead in pages. The lead's review_helper_patch also accepts stopped partials, but apply_helper_patch requires allowPartial=true for them. Partial application does not mark the task completed. Continue remaining work starts a fresh helper with instructions to inspect and preserve the recovered source, then finish what remains. Unfinished or conflicting recovery data stays separate; no patch is automatically applied and no AI work automatically resumes when Atlas opens. Helpers do not create ordinary chat tabs, separate game copies or Workshop uploads.

The feature was checked using isolated workspaces, mocked accounts/provider responses, the actual agent-session library, and native UI fixtures. Real account entitlement, service latency and quota consumption depend on the connected service. These improvements are included in the approved Atlas 0.3.8 public release.
